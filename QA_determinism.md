# QA: Determinism, Model Selection, and Security Boundaries

### 1. Why temperature 0 and seed 0, and does that guarantee identical output?
`temperature: 0` instructs the sampler to greedily pick the argmax token at each generation step, while `seed: 0` pins the pseudo-random generator state in inference runtimes that support it. On the exact same software stack, model weights, and hardware backend, this combination yields identical, reproducible token sequences in practice (as confirmed by our 3-pass determinism check across all dataset instructions). However, it does not provide an absolute mathematical guarantee across different environments. GPU floating-point non-determinism, batching dynamics, driver revisions, or CPU SIMD microcode differences can still introduce subtle logit shifts that occasionally flip a greedy boundary token.

### 2. What if the model gives a different tuple tomorrow or on another machine?
If hardware changes, quantization differences, or library updates produce a slight variation in the extracted tuple, the system's architecture prevents catastrophic failure. Every field in the tuple is strictly parsed and type-checked against our closed schema by `validate()`, replacing unrecognized structures with a safe fallback. Because semantic safety gates (the role matrix and intent rules) live entirely in deterministic Python code, a drifted tuple can only alter what action is requested, never grant permissions the caller's role is forbidden from having. In addition, keyword heuristics on `target` provide an independent safety floor, meaning baseline security controls remain intact even if extraction details drift.

### 3. Why qwen2.5:14b over qwen3:14b?
In our 30-case bake-off, `qwen2.5:14b` outperformed `qwen3:14b` on full-tuple accuracy (24/30 vs 22/30) and showed superior multilingual comprehension on Roman Urdu (8/10 vs 7/10). It was also noticeably faster and more consistent, averaging 7.5s mean latency compared to 9.4s for `qwen3:14b`. Both models tied on safety-critical edge cases with the same single fail-open event. Given its higher structural reliability, stronger code-switching performance, and lower inference latency on local hardware, `qwen2.5:14b` was the clear practical choice.

### 4. What happens if the extractor is wrong or the model is down?
If Ollama is unreachable, crashes, times out, or produces malformed JSON, `extract()` catches the exception and returns a canonical error tuple with `action="error"`. The policy engine enforces a strict fail-closed guarantee: any action not explicitly enumerated in `ALLOWED_ACTIONS` results in an immediate `DENY`. In addition, `run_pipeline()` wraps tool execution in a hard gate that executes tools only when the decision is strictly `ALLOW`. Therefore, an extractor failure or offline model completely halts execution without modifying the underlying database or executing any action.

### 5. Does the security depend on the model being correct?
No, the system's security boundary never relies on the model being correct or truthful. The reference monitor (`policy.py`) is written in deterministic, auditable code that operates independently of the LLM. The model merely parses untrusted natural language into a structured request tuple, and its safety flags (`is_bulk`, `sensitive`) are combined via logical OR with deterministic keyword target checks. As a result, the model can only raise risk (e.g., escalating `ALLOW` to `APPROVAL` or `DENY`), never lower it or bypass security checks.

### 6. What are the limits?
We must be honest about several real-world limitations. Our development set was used to tune few-shot examples and system prompts, meaning dev set metrics are naturally optimistic compared to raw real-world inputs. The test suites (48 dev cases, 12 held-out cases) are relatively small and do not exhaustively cover all regional slang or adversarial prompt injections. Furthermore, while extractor errors can mis-label an instruction—such as misclassifying an intended `delete_account` as a benign `view_record`—such mistakes can cause user annoyance, but can never trick the policy engine into performing an unauthorized action that the deterministic policy denies.
